# Gangolf production

Design: DiVoid #32404. This stack preserves the existing DiVoid/PostgreSQL dataset and named volumes. Docker commands target the configured daemon (`DOCKER_HOST=tcp://gangolf:2375`); env files and backup output are on the Docker client. No local path is assumed to exist on the remote host. No Compose plugin is needed.

Build the API from the `gangolf-api` directory using its Dockerfile; build ai-core from `ai-core`. Record immutable `sha256:` image IDs as `GANGOLF_API_IMAGE` and `GANGOLF_AI_CORE_IMAGE`. The checked-in stack pins the existing PostgreSQL17/pgvector, DiVoid PR229 and Processor images. Preserve these images for rollback.

Operations prepares a private directory (`GANGOLF_CONFIG_DIR`, mode0700), with mode0600 files `postgres.env`, `divoid.env`, `processor.env`, `api.env`, `ai-core.env`. These are Docker env-file data, not shell scripts. Never commit or print them. Set the following explicitly, preserving actual credentials and local graph IDs:

* postgres: `POSTGRES_DB=divoid`, `POSTGRES_USER=postgres`, `POSTGRES_PASSWORD` (existing bootstrap credentials).
* divoid: `Database__Type`, `Database__Host=divoid-processor-alpha-pg`, `Database__Port`, `Database__Instance`, `Database__User`, `Database__Password`, `DIVOID_KEY_PEPPER`, `Embedding__ModelPath=/data/models/embeddinggemma-2`. Use the qualified dedicated non-superuser app role; preserve the pepper.
* processor: `PROCESSOR_HTTP_ADDR=:8080`, `PROCESSOR_WORKSPACE_DIR=/data/workspace`, `PROCESSOR_MODEL_URL=http://127.0.0.1:11434`, `PROCESSOR_MODEL_PROTOCOL=ollama`, `PROCESSOR_MODEL_ID=gemma4:latest`, local `PROCESSOR_DIVOID_URL` and `PROCESSOR_DIVOID_KEY`. Qualify the URL shape against the installed Processor.
* api: `GANGOLF_LISTEN=127.0.0.1:8092`, `GANGOLF_DIVOID_API_URL=http://127.0.0.1:8091/api`, `GANGOLF_DIVOID_TOKEN`, `GANGOLF_API_KEY_PEPPER`, local `GANGOLF_DIVOID_ROOT_ID`, `GANGOLF_DIVOID_MESSAGES_ID`, `GANGOLF_DIVOID_CONFIG_ID`, `GANGOLF_TWITCH_CREDENTIAL_DIR=/run/gangolf-credentials`.
* ai-core: `GANGOLF_API_URL=http://127.0.0.1:8092`, `GANGOLF_API_KEY`, canonical numeric `GANGOLF_TWITCH_BOT_USER_ID`, `GANGOLF_CHANNELS`, `PROCESSOR_URL=http://127.0.0.1:8080`, local `PROCESSOR_SUBJECT`, `PROCESSOR_CONFIG`, `PROCESSOR_MEMORY_CONFIG`. Preserve approved chat/memory policy semantics, gemma4:latest and thinking off.

Operations verifies port8092 is free, the local model is ready, all external named volumes/networks exist, and seeds `gangolf-production-twitch-secrets` through stdin, with file `twitch-gangolf`, UID10001/mode0400. Mount that volume read-only; a tmpfs populated only once loses credentials on restart. Never mount the workstation secret path on the remote daemon. Qualify UID10001 access and runtime credentialRef mapping.

Run `python3 start.py`. It starts PG, waits readiness, then DiVoid, Processor and API in order. Existing containers are retained; operations reconciles their environment, network, mounts and restart policy before adoption. The script rejects image mismatches and never deletes containers/volumes. Existing DiVoid container names and volumes are intentional. For first adoption, operations preserves rollback containers before replacing any conflicting name. Restart policy is `unless-stopped`; Docker host restart does not guarantee dependency order, so application retry/restart and ordered readiness must be validated by operations.

Default startup leaves ai-core off. Only after observing the previous responder stopped, start with `GANGOLF_PREVIOUS_RESPONDER_STOPPED=yes python3 start.py --responder`. The API itself may connect IRC when configured, so operations must coordinate the single-responder window before API activation as well. Rollback stops new ai-core/API first, then restores preserved old runtime/config, retaining all graph writes and volumes. Never run two responders. This script does not disable Mamgo services.

## Backup and isolated restore

Set `GANGOLF_BACKUP_DIR` to a private directory on the client machine. `python3 backup.py` streams custom-format pg_dump, roles/globals, container metadata, protected config and the durable Twitch secret volume to a private staging directory. It publishes a checksummed backup only when every command succeeds, then retains seven completed copies. Failed staging directories remain private for diagnosis and do not trigger pruning. The remote Docker host to client copy is off-host relative to Gangolf; availability still depends on the client being online. Protect and encrypt the client filesystem/backup destination. Dumps/config archives contain secrets; never upload them to DiVoid or attach them to PRs.

Install `backup.py` at `~/.local/share/gangolf-production/backup.py`; install the two unit files under `~/.config/systemd/user/`. Create protected `~/.codex/secrets/gangolf-production/backup.env` with `DOCKER_HOST`, `GANGOLF_CONFIG_DIR`, `GANGOLF_BACKUP_DIR`, `GANGOLF_API_IMAGE`; then `systemctl --user daemon-reload` and `systemctl --user enable --now gangolf-backup.timer`. Verify timer and a successful first service run. This is daily logical backup, target RPO<=24h and seven copies, conditional on monitored client availability; it is not HA. For unattended operation ensure the user manager survives logout. Operations owns installation/activation.

Run `python3 restore.py BACKUP_DIRECTORY --name gangolf-restore-UNIQUE`. It verifies checksums, refuses existing targets and restores into a new isolated volume/container with no network or published port. It retains the result for operations' independent validation. A successful restore command is only a checkpoint: compare users/keys/nodes/relations/content, pgvector and app role privileges, start an isolated DiVoid with preserved pepper and authenticate both service identities; never restore over production for a test. Protected archives restore config/credentials separately under operator control. After validation, remove only that exact isolated container and volume. Take and qualify a backup before role/config/container replacement.
